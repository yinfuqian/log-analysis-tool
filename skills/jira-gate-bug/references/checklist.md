# 缺陷单完整性检查清单

本清单是「缺陷单提交后门禁」的默认判定依据：缺陷单进入研发处理前，先确认提单信息是否足够定位问题。

- **检查入口**：缺陷单提交后（状态通常是「待处理 / 新建」）。
- **检查范围**：现象、复现、环境、时间、证据、影响面；不检查实现细节，也不评价修复方案。
- **判定结果**：`不通过`（打回补充） / `通过`（可流转，或继续走自查与自动分析）。

## 检查项等级

| 等级 | 含义 | 影响 |
|---|---|---|
| `MUST` | 缺任一项即打回 | 打回补充 |
| `SHOULD` | 建议补充，记录但不打回 | 评论区提示 |
| `REDLINE` | 一票打回红线 | 直接打回 |

判定必须能指向具体证据：字段值、描述段落、附件文件名、评论时间点。找不到证据记为「证据不足」，不允许凭印象写“已满足”。

## 1. MUST：缺任一项即打回

| 编号 | 检查项 | 判定要点 | 证据位置 |
|---|---|---|---|
| 1.1 | 概要一句话说清现象 | 含对象/模块 + 现象，不是「报错」「有问题」「系统异常」这类无信息标题 | 概要字段 |
| 1.2 | 现象与期望结果 | 明确「期望发生什么」与「实际发生什么」，两者能直接对比 | 描述 |
| 1.3 | 复现步骤 | 可执行的入口、操作、数据；偶现问题需给出发生频率与最近一次时间 | 描述 |
| 1.4 | 发生环境 | 客户/项目、环境（生产/测试/预发）、产品与模块 | 环境字段 / 自身字段 / 描述 |
| 1.5 | 影响的版本 | 版本号、Tag 或分支；多版本影响时逐条列出 | 影响的版本 / 描述 |
| 1.6 | 时间信息 | 故障发生时间（含时区）或时间段，能与日志时间对齐 | 描述 / 评论 |
| 1.7 | 证据附件 | 至少一份与该现象对应的日志、截图或接口返回；日志需覆盖故障时间点 | 附件 |
| 1.8 | 影响范围 | 受影响用户/业务范围，是否阻塞主流程 | 描述 |

## 2. REDLINE：一票打回

- 只有标题、正文为空或只有一句「系统报错」。
- 描述与附件互相矛盾（例如描述的是 A 接口，日志里全是 B 接口）。
- 日志附件为空文件、被截断到无法定位，或明显与故障时间不符。
- 截图无法辨认（全黑、模糊、只有无关页面），且没有其它证据。
- 附件损坏、加密、需要密码才能打开。
- 复现步骤缺失且日志无法定位问题（偶现问题除外，但必须提供时间点与频率）。

## 3. SHOULD：记录但不打回

- 客户名称、提单人、所属项目阶段。
- 关联需求单、发布单、变更单链接。
- 附件命名是否体现环境与时间。
- 期望修复时间、优先级说明。
- 是否已自查（自查结果由 [self-check.md](self-check.md) 单独判定）。

## 4. 与自动分析的联动

第 4 步「自动故障分析」还需要产品、模块、仓库地址与版本：

- 1.4 / 1.5 已覆盖产品、模块与版本；仓库地址由工具里模块绑定的分支自动带出。
- 上述信息只能由调用方 `inputs` 或缺陷单字段提供时，**不允许猜测**：按 SKILL.md「缺分析参数」模板写评论，门禁字段写 `未检查`。

## 5. 项目自定义

若缺陷单所属项目另有成文的《缺陷单规范》或提单模板，以项目规范为准：

- 在评论里注明依据来源（项目规范名称 / 链接）。
- 项目规范与本文冲突时，采用更严格的一方。
