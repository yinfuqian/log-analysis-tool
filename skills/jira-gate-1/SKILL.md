# Jira 需求准入检查

用户给一个 Jira 需求链接，你自己打开它，读完描述、附件、依赖、子任务和历史评论，按准入清单逐项判定，给出**需求难度分级**和**是否达标**；把检查项清单写进这张单子的评论区。

## 交付物

**唯一合规交付物是 Jira 评论**：

1. Jira 评论：**只列检查点**——一行难度结论 + 逐项打标记的检查项清单（`(/)` 通过、`(x)` 不通过）；达标与不达标用同一套结构（模板见本文档「输出模板」节）。
2. 对话里的摘要：难度（高/中/低）+ 达标/不达标 + 关键理由，供用户即时看到结果。

评论以**可执行、可扫读**为目标：让人 30 秒内顺着红叉看清「卡在哪、要补什么」，绿勾项一眼带过。

**不要在本地生成报告文档（Markdown/HTML/Word 等）作为交付物。** 结论只进 Jira 评论区；本地仅允许在临时目录存放附件与解析中间文件（如 `<工作目录>/work/jira-gate/<KEY>/attachments/`），这些中间文件不是交付物，也不要放进 outputs 目录。

## 判定依据

检查项、等级（`MUST` / `CONDITIONAL` / `SHOULD` / `OBSERVE`）与一票退回红线以 [references/checklist.md](references/checklist.md) 为准（清单只保留检查项与判定规则，章号 `5.x` / `6.x` / `7.x` / `10` / `11` 沿用标准版编号）。**先读它再开始判定**，不要凭印象发明标准。难度分级算法与评论模板见本文档 §5、§7 与「输出模板」节。

**门禁口径（v3，避免误伤）**：判定主体是产品组标准版清单。以下内容**不作为 G1 阻断项**，最多记为“排期前补齐”或“相关角色补充”：

- Jira 单据字段的填写情况（客户名称、影响的版本、标签、模块、经办人等）。
- 测试数据准备、测试环境与数据构造细节。
- 纯技术实现细节（Java 类、接口实现、数据库字段、SQL、组件、线程池、部署参数等）。
- 工作量评估与子任务拆解（checklist §6.7.1）：`CONDITIONAL`，不进入红线，在检查项清单的 6.7.1 行注明「不阻断 G1，排期前补齐」。

阻断项只来自三处：checklist §5 的 `MUST`、§6 已触发的 `CONDITIONAL`、§10 一票退回红线。

## 执行步骤

### 0. 运行环境适配（先读这一节）

本技能有两种运行环境，**取数通道不同，判定标准完全相同**：

- **桌面 Codex（带 `node_repl` 工具）**：按下面「通道 A」的 `node_repl` 片段执行。
- **服务器容器 / `codex exec`（没有 `node_repl`）**：用 shell 直接执行技能自带命令行入口 `scripts/jira-cli.mjs`（能力与 `node_repl` 通道一致）：

  ```bash
  # 令牌与连通性自检；令牌来自 --token、JIRA_TOKEN 环境变量或技能目录下的 .jira-token
  node <技能目录>/scripts/jira-cli.mjs selftest
  # 读取需求单并输出紧凑 Markdown 摘要（判定依据）
  node <技能目录>/scripts/jira-cli.mjs get <KEY|URL>
  # 下载附件到工作目录
  node <技能目录>/scripts/jira-cli.mjs attachments <KEY|URL> work/jira-gate/<KEY>/attachments
  # 写入评论：正文先落文件再提交，避免多行标记转义问题
  node <技能目录>/scripts/jira-cli.mjs comment <KEY|URL> --file work/jira-gate/<KEY>/comment.txt
  ```

  附件解析仍走 Python：`python <技能目录>/scripts/extract.py <附件目录> --out <附件目录>/../attachments.txt`。

  自检中「校验令牌」步骤返回 401 只表示该令牌无权访问 `/myself` 账户接口，**不等于令牌失效**：
  只要「访问 Jira」步骤成功、且 `get <KEY|URL>` 能取到需求单，就继续按流程完成检查。

  在该环境中不要尝试调用 `node_repl`，也不要因为缺少桌面工具而降低判定标准。

### 1. 解析单号

`parseIssueKey()` 支持 `/browse/KEY`、`?selectedIssue=KEY`、jql 链接、纯 `KEY` 四种输入。

### 2. 取数：通道 A —— Jira REST（首选）

在 `node_repl` 工具里执行下面的代码。**注意本机沙箱限制**：PowerShell 无法建立 TLS 连接，`node_repl` 是唯一能访问 Jira 的通道；`node_repl` 内没有 `process`、不支持静态 import，所以脚本必须用 `await import()` 动态加载，且**不要在 node_repl 顶层引用 `process`**。

```javascript
// <SKILL_DIR> = 本 SKILL.md 所在目录的绝对路径（如 C:/Users/xxx/.codex/skills/jira-gate-1）
const j = await import("file:///<SKILL_DIR>/scripts/jira.mjs");
const st = await j.selftest();              // 先自检：令牌、连通性、账号
nodeRepl.write(JSON.stringify(st, null, 1));
```

只有 `jira.mjs` 的导入路径需要按实际安装位置替换；脚本内部全部按自身位置解析，不依赖固定目录。

自检通过后取数：

```javascript
const issue = await j.getIssue("CALL-1446");        // 也接受完整 URL
nodeRepl.write(j.renderIssueMarkdown(issue));        // 紧凑摘要，不要直接打印原始 JSON
const files = await j.downloadAttachments(issue.key, "<工作目录>\\work\\jira-gate\\CALL-1446\\attachments", { issue });
```

- `getIssue()` 返回规范化对象：描述、自定义字段（中文名）、附件、问题链接、子任务、评论、工时。
- `renderIssueMarkdown()` 是控制上下文的关键，用摘要做判定；只有摘要被截断时才回到原始对象取局部字段。
- 附件下载后用内置 Python 解析文本（脚本只支持动态导入，Python 走 PowerShell）：

```powershell
# $py 用 load_workspace_dependencies 返回的 Python 路径；<SKILL_DIR> 同上一层说明
& $py "<SKILL_DIR>\scripts\extract.py" "<附件目录>" --out "<附件目录>\..\attachments.txt"
```

若环境里已有可用的 `python`（需带 pdfplumber / python-docx / openpyxl / python-pptx），直接 `python extract.py ...` 也可以。

支持 `docx / pdf / xlsx / pptx / txt / md / json / xml / csv / html`；**解析失败要如实记为"无法解析"**，不能当成"附件没有内容"。图片附件用图像查看能力看，不做臆测。

附件是压缩包时脚本会先解压再递归解析（`.zip / .rar / .7z / .tar / .tar.gz / .tgz / .gz / .bz2 / .xz`），解压产物放在 `<附件目录>\__unpacked\`，输出里用 `压缩包名/内部路径` 标明每个文件的来源：

- **`.rar` 是重点**：本机通常没装 WinRAR / 7-Zip，脚本会自动降级调用 Windows 自带的 `tar.exe`（bsdtar），实测能解 RAR5；再依次尝试 `7z` / `7za` / `unrar`。
- 引用证据要写到压缩包内部，例如 `附件.rar/xxx_PRD_DELIVERY.md §5.2.1`、`附件.rar/xxx_Prototype.html`。
- 解压失败时会输出 `[压缩包解压失败]` 及尝试过的命令与报错，**这种情况必须如实记为"附件无法解析"，不能当成"附件没有内容"，也不要臆测包内内容**。
- 可选 `--unpack-dir <目录>` 指定解压位置；默认的 `__unpacked` 目录在遍历时会跳过，不会重复解析；同名解压结果自动加 `-2` 后缀，不覆盖上一次结果。

### 3. 取数：通道 B —— 应用内浏览器（无令牌时兜底）

没有配置令牌时，用已登录的应用内浏览器打开需求单：

1. `cua.createBrowserTab("iab", issueUrl)` 打开单子。
2. 用 `tab.playwright.evaluate(() => document.body.innerText)` 取正文，可拿到概要与描述、附件列表、问题链接、子任务、评论。
3. 附件：点击附件链接触发下载，再对下载目录跑 `extract.py`（压缩包会自动解压，见上一节）。
4. 结论评论：在页面评论区输入并提交。

注意：Jira 的 `/rest/...` 地址在浏览器里会被拦截（`ERR_BLOCKED_BY_CLIENT`），**不要在浏览器里访问 REST 地址**；浏览器只用于读页面和写评论。通道 B 的结论必须注明"基于页面内容检查"。

### 4. 逐项判定

对 `references/checklist.md` 的每条检查项给出：`通过` / `不通过` / `不适用（附理由）` / `证据不足`，并写明**证据位置**（字段名、描述段落、附件名，必要时页码或行号）。

逐项判定表在对话回复里呈现；写入 Jira 评论时按 §7 组织检查项清单（逐项带标记），不要搬运难度维度取值与判定过程。

- 结论必须能指向具体证据；找不到证据就是"证据不足"，不许写"已满足"。
- 答案若已存在于需求单、附件或历史评论中，自己核对出结论，不要把检索工作反问给产品经理。
- 现有资料无唯一答案、且不同答案会改变产品规则/行为/状态/权限/AC 的，才列入"需要产品确认"，并给出具体问题与直接建议。
- 纯技术实现细节（Java 类、接口实现、数据库字段、SQL、组件、线程池、部署参数等）不作为不达标理由。

### 5. 需求难度分级

每维度按 3（高）/ 2（中）/ 1（低）取值：

| # | 维度 | 高（3） | 中（2） | 低（1） |
|---|---|---|---|---|
| 1 | 业务复杂度 | 多角色多场景，规则需决策表 | 单角色多分支 | 单点功能或配置 |
| 2 | 跨系统与依赖 | 跨 3 个以上系统 / 外部客户系统 / 第三方协议 | 跨 2 个系统 | 系统内自闭环 |
| 3 | 状态与权限复杂度 | 多状态迁移 + 多角色权限差异 | 有状态或权限差异之一 | 无状态与权限差异 |
| 4 | 数据与兼容性 | 需数据迁移、双轨、历史兼容 | 有存量数据或旧版本影响 | 全新数据，无兼容负担 |
| 5 | 非功能承诺 | 有并发 / 时延 / 安全 / 合规硬指标 | 有常规性能或安全要求 | 无非功能承诺 |
| 6 | 不确定性与风险 | 存在未定的关键规则、新协议、新领域 | 局部待确认 | 方案明确，无未决 |
| 7 | 范围与工作量 | 多模块、子任务多、工期长 | 单模块中等 | 小改动 |

- 总分（7–21）：**≥17 高 / 10–16 中 / ≤9 低**。
- **一票升级**：命中资金 / 计费 / 合同承诺、不可逆数据操作、合规或隐私承诺、核心链路性能承诺、跨公司或多方联调之一 → 至少为「中」；命中两项及以上，或涉及资金 / 计费 / 合规 → 直接为「高」。
- **必须算出维度取值**，不能拍脑袋给结论；维度取值写在对话回复里，评论只写难度结论加一句依据。

难度影响评审强度：高难度必须开评审会、技术方案单独评审，且要求性能 / 安全 / 兼容专项结论；中难度常规评审；低难度可简化书面确认。**难度分级不降低任何 `MUST` 要求。**

### 6. 得出达标结论

- **达标**：所有 `MUST` 与已触发的 `CONDITIONAL` 满足，且未命中任何一票退回红线（checklist §10）。
- **不达标**：命中红线，或存在未满足的 `MUST` / 已触发 `CONDITIONAL`。
- 难度高低不影响达标标准：高难度需求也可以达标，低难度需求也可能因缺验收标准而不达标。
- `SHOULD` 缺失只记录取舍，不单独阻断。
- 5.2.1（背景与价值）与 5.8.1（验收标准可测）属 `MUST`，未满足即不达标。
- 6.3.1（依赖项）与 6.6.1（非功能要求）仅在触发时按 `MUST` 处理；未触发时记为“不适用”并写明依据。
- 6.7.1（工作量与子任务）**不阻断 G1**：即使为空，也只在检查项清单的 6.7.1 行注明「不阻断 G1，排期前补齐」，不因此判不达标。

### 7. 组织评论内容

按本文档「输出模板」节的模板组织正文。**达标与不达标用同一套结构**，差别只在标题措辞与每项标记。评论正文**只有检查点**：

- 一行元信息：难度 + 检查对象 + 依据 + 预检时间。
- 检查项清单：逐项列出本次实际判定过的检查项，每项一行、行首必须带标记。

**检查项清单的写法**

- 标记：通过写 `(/)`（绿勾），不通过写 `(x)`（红叉）。两者都必须显式写出，不允许留空或省略。
- 通过项：只写 `(/) *编号 名称*（等级）`；确有必要说明边界时，最多补一句 30 字以内的结论。
- 不通过项：写 `(x) *编号 名称*（等级）：问题 → 要补什么；证据：位置`。
- 未触发的条件项：写 `(/) *编号 名称*（CONDITIONAL，未触发）：判断依据`。
- 排列顺序按 checklist 章号（如 5.1.1 → 5.2.1 → 5.8.1 → 6.3.1 → 6.7.1），便于与清单逐条对照。

**清单范围**：checklist §5 全部适用项 + §6 全部相关项（含未触发项）+ §10 红线项。判定过的项都要出现，**不得只列不通过项**。

**不写**（这些留在对话回复里）：难度维度逐项取值、检查过程说明、`SHOULD` 级建议、需产品确认的开放问题（并入对应检查项行的「要补什么」）。

硬约束：

- 不通过项全部列出，**不做删减**——精简的是表述，不是缺口。
- 通过项一行一项；不通过项每条 ≤ 80 字；评论总长建议 ≤ 1500 字符（检查项多时可放宽到 2500）。
- 不要用表格（列宽大、手机上难读），用有序列表。
- 评论正文必须使用 Jira wiki 标记渲染，不要用 Markdown。格式对照见 `references/jira-api.md` §8。

### 8. 写 Jira 评论

- 写入前用 `mypermissions` 做一次只读权限预检（见 `references/jira-api.md` §7）；`ADD_COMMENTS=false` 时不要反复重试，直接告知用户缺权限。
- 用户已明确要求把结论落到评论时，直接写入，并在对话里同步摘要。
- 只有用户要求"先看草稿""不要写"时，才改为只展示内容不写入。
- 复审同一张单子时，先 `findPreviousReviews(key)`；有历史预检评论时**只在原评论下回复复审结论**（按最新判定重新打标记：本次已补的项由 `(x)` 变为 `(/)`，仍缺的项保持 `(x)`），不要新增第二条完整预检评论。
- 达标与不达标都写入同一套检查项清单：达标时标题写「达标（可进入下一步评审）」，各项按实际判定打 `(/)` 或 `(x)`，不再单独写「达标理由 / 风险建议」段落。

### 9. 回写门禁字段（用于 Jira 工作流门禁）

若 Jira 侧已配置 G1 门禁字段，写完评论后**必须**把结论回写，供工作流校验器/条件读取：

```javascript
const gate = await j.setGateResult(key, { result: "通过", difficulty: "高" });  // 不达标时 result 写 "不通过"
nodeRepl.write(JSON.stringify(gate));
const back = await j.getGateResult(key);        // 写入后读回确认
```

- 字段不存在时返回 `{ skipped: true, reason, hint }`：**不要报错、不要重试、更不要伪造字段名**，照常交付评论，并在对话里说明"该 Jira 尚未配置门禁字段，本次仅留评论"。
- 字段名默认按 `G1准入结论` / `G1需求难度` / `G1预检时间` 依次匹配；实际字段名不同时，在 `~/.codex/jira/config.json` 用 `gateResultField` / `gateDifficultyField` / `gateCheckedAtField` 覆盖，不要改脚本。
- 取值约定：达标写 `通过`，不达标写 `不通过`；`6.7.1`（工作量与子任务）未满足**不改变** `result`，因为它不阻断 G1。
- 评论与字段必须一致：先写评论，再写字段；复审后结论有变化时重新回写一次。

## 输出模板（Jira 评论）

结论**只以 Jira 评论形式留痕**，不额外生成本地报告文档。评论**只列检查点**：达标与不达标结构相同，只在标题措辞与每项标记上不同。

**通用结构**

```text
h3. G1 需求准入 AI 预检：{{达标（可进入下一步评审） / 不达标（退回补充）}}

* 难度：{{高/中/低}} | 检查对象：{{PRD 附件名与版本}} + {{原型 / 本单描述}} | 依据：PRD 需求准入 Checklist
* 预检时间：{{时间}}（AI 预检，最终以产品架构师确认为准）

h4. 检查项

# (/) *5.1.1 需求来源*（MUST）
# (x) *5.2.1 背景与价值*（MUST）：{{问题一句话}} → {{要补什么}}；证据：{{位置}}
# (/) *5.4.1 功能需求*（MUST）
# (x) *5.8.1 验收标准可测*（MUST）：{{问题}} → {{要补什么}}；证据：{{位置}}
# (/) *6.3.1 依赖项*（CONDITIONAL，未触发）：{{判断依据}}
# (x) *6.6.1 非功能要求*（CONDITIONAL）：{{问题}} → {{要补什么}}；证据：{{位置}}
# (x) *6.7.1 工作量与子任务*（不阻断 G1，排期前补齐）：工时与子任务为空，由研发负责人补齐
```

**标记规则**

| 情形 | 标记 |
|---|---|
| 该检查项通过 | `(/)` 绿勾 |
| 该检查项不通过 | `(x)` 红叉 |

- 每个检查项**必须**有标记，通过项也要写 `(/)`，不要省略。
- 只有不通过项才写「问题 → 要补什么；证据」；通过项只写编号与名称。
- `6.7.1` 不阻断 G1，但仍按实际填写情况打标记，并在括号里注明「不阻断 G1，排期前补齐」。

## 预检规范

**取数范围**（以 Jira 需求单为唯一入口）

- 主单字段：类型、概要、描述、优先级、客户名称、产品归属、影响的版本、经办人、标签、模块、工时 / Story Points。这些字段是**定位与证据来源**，字段缺失本身不构成不达标。
- 附件：接口文档、PRD、原型、截图、数据样例（含版本与提供方）；压缩包需解压后逐项阅读。
- 问题链接：前置、阻塞、被阻塞、关联需求。
- 子任务与子任务状态。
- 历史评论与改动记录：判断“待确认”是否已被回答、需求是否已升版。

**证据要求**

- 每条判定必须指向**具体证据位置**：字段名、描述段落、附件文件名（必要时页码或行号）、评论时间点。
- 不允许无证据的“已满足”；找不到证据一律记为“证据不足”。
- 证据冲突时（描述与附件结论不一致）记为“需要产品确认”，不自行选择其一。
- 附件位于压缩包内时，证据写到内部路径，例如 `附件.rar/xxx_PRD_DELIVERY.md §5.2`。

**禁止事项**

- 不把“检索工作”反问给产品经理；不因为某项无法判定而停止其余项的检查。
- 不编造需求未写明的内容，不把推测写成已确认事实。
- 不把纯技术实现细节、单据字段缺失、测试数据未准备包装成 G1 阻断项。
- 不因难度高或低而放宽 `MUST` 与红线。
- 不擅自修改需求单字段、不流转状态、不指派经办人。
- 不生成报告类文档作为交付物；不在需求单中留下未完成的草稿评论。

## 令牌配置

`jira.mjs` 按顺序查找令牌文件：skill 目录下的 `.jira-token` / `.jira-token.txt` / `jira-token.txt`、`~/.codex/jira-token.txt`、`~/.codex/jira/config.json`（支持 `{"token":"...","baseUrl":"..."}`）。

- 令牌来源：Jira → 右上角头像 → 个人访问令牌 → 创建令牌（Jira 10.3 Server 已启用 PAT）。
- 令牌只用于 `Authorization: Bearer`，不要打印、回显或写进报告文件。
- `selftest()` 返回未找到令牌时，直接告诉用户按上面的路径放好令牌文件，并说明放好后可以立刻重试；同时可以先用通道 B 兜底完成检查。

## 硬性约束

- 不流转状态、不指派经办人；除下面这一项外不修改任何需求单字段。
- **唯一允许写入的字段是 G1 门禁字段**（`setGateResult()` 写入的准入结论/难度/预检时间），它是评论结论的机器可读副本，不是新的事实来源。
- 不生成本地报告文档作为交付物；判定结果以 Jira 评论为唯一留痕。
- 不编造需求未写明的内容，不把推测写成已确认事实。
- 依赖项、非功能要求、工作量与子任务都要检查并记录，但按下列等级处理：只有 5.2.1 / 5.8.1 / 已触发的 6.3.1 / 6.6.1 与 §10 红线才判不达标，6.7.1 在清单里注明「不阻断 G1，排期前补齐」。
- 不把单据字段缺失、测试数据未准备、纯技术细节当作不达标理由。
- 不留下未完成的草稿评论。
