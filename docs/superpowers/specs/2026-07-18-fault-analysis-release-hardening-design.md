# 故障分析工具发布加固设计

## 1. 背景与目标

项目能力已经从单一日志解析扩展到日志文件、日志截图、业务截图、多图、代码仓库、上下游链路、知识库和操作审计，因此对外名称统一调整为“故障分析工具”。本次发布加固同时解决模型配置分散、提示语不完整、源码缺少维护说明、构建产物混杂、README 过时以及 Docker 只能部分验证的问题。

本次目标是产出一套可重复构建、可自检、可部署、可维护的完整交付物。构建成功必须代表后端、Worker、前端、数据库迁移、Redis、Git、用户文件、AI 配置和 OCR 主链路均具备明确的可用性验证，不能只验证 OCR 或只验证代码能够编译。

## 2. 范围

### 2.1 包含范围

- 对外产品名称、客户端标题、前端标题、公告、文档和构建产物统一为“故障分析工具”。
- AI 模型默认配置为 `gpt-5.6-sol`，文本、日志、单图和多图使用同一模型配置。
- 新增可配置的深度推理强度，默认使用高强度推理。
- 为自有生产源码的模块、类、函数、配置项和复杂业务分支补充中文说明。
- 重写根 README，并补齐 Windows 客户端 README、Docker 构建、部署、迁移、账号管理、OCR、模型和故障排查说明。
- 完善后端、前端 Dockerfile 和根 Compose，使其能够构建并启动完整依赖栈。
- 增加构建期与运行期自检，覆盖核心依赖、应用加载、Worker、迁移、Git、OCR、前端和服务健康状态。
- 安全删除可重新生成的缓存、日志、旧构建产物和临时文件。
- 补全登录、申请账号、输入类型、多图、OCR 降级、模型加载、任务失败、结果展示和导出等提示语。

### 2.2 不包含范围

- 不重命名现有数据库表、历史迁移版本和对外 API 路径。
- 不修改第三方依赖、`node_modules`、生成代码和历史迁移文件的注释。
- 不删除现有有效源码、测试、配置示例、设计文档和用户数据文件。
- 不把真实密钥、密码或生产地址写入镜像和版本库。

## 3. 命名与兼容策略

用户可见名称统一为“故障分析工具”，英文构建标识使用 `FaultAnalyzer`：

- Windows 客户端：`FaultAnalyzerClient.exe`
- macOS 客户端：`FaultAnalyzerClient.app`
- 前端页面标题：`故障分析工具`
- 登录窗口标题：`故障分析工具登录`
- 本地默认镜像：`fault-analysis-tool`

为避免破坏已有客户端会话、接口调用和数据库数据，以下内部标识暂时保留：

- 现有 `/analysis`、`/logfile` 等 API 路径
- 数据库名和历史表名
- 已发布的会话存储键
- Python 内部兼容类名和已有迁移标识

内部临时目录和新建脚本采用 `fault-analyzer` 命名；旧目录仅在兼容读取时保留。

## 4. AI 模型与深度推理

配置中心新增并统一使用：

```env
OPENAI_MODEL=gpt-5.6-sol
OPENAI_REASONING_EFFORT=high
```

所有 AI 调用通过同一参数构造函数生成请求参数：

- Chat Completions 风格使用 `reasoning_effort`。
- Responses 风格使用对应的 `reasoning.effort` 结构。
- 配置为空时不发送推理参数。
- 第三方接口明确拒绝推理参数时，返回包含模型名、接口风格和拒绝原因的中文错误，不静默降级成浅层分析。
- 日志中不记录 API Key、Token、用户密码和图片原始敏感内容。

配置测试必须覆盖默认值、环境变量覆盖、Chat 风格和 Responses 风格请求参数。

## 5. 注释与可维护性规范

注释覆盖自有生产源码，不做逐行翻译式注释：

- Python 文件增加模块说明；公共类、公共函数和复杂内部函数增加中文 docstring。
- Vue/JavaScript 对组件职责、状态流转、认证、请求封装和复杂判断增加中文注释或 JSDoc。
- Shell、Batch、Dockerfile、Compose 和环境变量示例说明输入、输出、失败条件和安全注意事项。
- 配置项说明默认值、使用位置和生产影响。
- 复杂分支解释“为什么这样处理”，不重复描述代码表面行为。

测试、历史迁移、自动生成文件和第三方代码不强制补充注释。新增注释不得改变现有业务行为。

## 6. Docker 完整构建设计

### 6.1 后端镜像

后端镜像固定使用受支持的 Python 3.10 基线，并执行以下构建检查：

1. 安装系统依赖：Git、证书、OCR 运行库和健康检查工具。
2. 安装锁定的后端与 OCR Python 依赖。
3. 执行 `pip check`。
4. 执行 Python 全量 `compileall`。
5. 导入并创建 Flask 应用，确认路由表可生成。
6. 导入 Celery 应用并确认任务已注册。
7. 导入数据库迁移和初始化脚本。
8. 检查 Git 命令可执行。
9. 初始化 PaddleOCR、下载模型并对构建期生成的测试图片执行真实预测。
10. 运行不依赖外部数据库和 Redis 的核心冒烟测试。

任何步骤失败都使镜像构建失败。OCR 模型缓存写入镜像内的 `/data/paddle-cache`，首次挂载命名卷时由 Docker 初始化到卷中，后续启动复用。

### 6.2 前端镜像

前端使用 Node.js 20 多阶段构建：

1. 使用 `npm ci` 按锁文件安装依赖。
2. 执行前端单元测试和生产构建。
3. 使用 Nginx 提供静态文件。
4. Nginx 配置支持前端路由回退、静态缓存和 `/api` 反向代理。
5. 运行健康检查验证首页可访问。

### 6.3 Compose 服务

根 Compose 默认提供自包含环境：

- `mysql`：持久化数据库和健康检查
- `redis`：Celery Broker、结果存储和健康检查
- `migrate`：一次性初始化与迁移任务
- `api`：Gunicorn API 服务
- `worker`：Celery Worker
- `frontend`：Nginx 前端服务

启动顺序使用健康状态约束：MySQL/Redis 健康后运行迁移，迁移成功后启动 API 和 Worker，API 健康后前端对外服务。外部 MySQL/Redis 通过独立的 Compose 环境变量覆盖，不要求修改镜像。

### 6.4 构建与运行期自检

提供统一的后端验证脚本，支持：

- `--build`：不连接外部服务，检查导入、路由、Worker、Git 和 OCR。
- `--runtime`：检查数据库、Redis、用户 CSV、上传目录、模型缓存和关键配置。
- `--ocr`：单独执行 OCR 模型初始化与预测。

API 提供存活和就绪检查。存活检查只判断进程；就绪检查验证数据库、Redis、用户文件和关键目录。Worker 使用 Celery ping 或等价命令验证。

## 9. 提示语设计

提示语遵循“当前状态、正在做什么、用户下一步”三部分：

- 登录失败区分用户不存在、密码错误、禁用和立即下线。
- 账号申请说明必填项、提交状态和管理员联系方式。
- 图片输入明确区分日志截图和业务截图。
- 多图提示说明逐张分析、重复错误合并规则和图片序号。
- OCR 首次加载提示耗时；不可用时说明仍将使用原图多模态分析。
- AI 深度推理阶段提示预计等待，不把长时间推理显示为卡死。
- 后端、数据库、Redis、Git、OCR 和 AI 服务错误分别给出中文原因。
- 结果页说明问题数量、证据来源、置信度和命令执行风险。

## 12. 风险与回退

- OCR 模型下载依赖构建网络。模型源不可访问时构建应失败并给出下载错误；可通过预置模型缓存或内部镜像源解决。
- `gpt-5.6-sol` 和推理参数由第三方接口提供，需用真实接口冒烟验证；接口不兼容时通过环境变量关闭推理参数或调整 API 风格。
- 全栈 Compose 默认值不能直接用于生产，生产必须替换密码、域名和密钥。
- 外部兼容标识暂不重命名，降低本次发布风险。需要彻底内部重命名时另开迁移版本。
